# project2 要件定義書

## 1. 概要
- 個人のタスク/生活管理を中心機能とし、将来的にデータ/ファイル処理ツールなどを追加できる、ログイン制の多機能Webアプリ。
- サーバ公開は行わず、ローカル環境での実行のみを前提とする。
- 開発はテスト駆動開発（TDD）で進める。拡張性を重視し、機能追加が既存機能を壊さない構成にする。

## 2. 技術スタック
| 項目 | 選定 | 理由 |
|---|---|---|
| バックエンド | Python / FastAPI | 型付けがしやすく、テストが書きやすい。将来のデータ処理機能とも相性が良い |
| フロントエンド | 素のHTML/JS（Jinja2テンプレートでFastAPIから配信） | 現時点で習熟している技術で開始。機能が増えて管理が煩雑になった場合はReact等への移行を別途検討 |
| データ保存 | SQLite | ローカル実行のため無料。1ファイルで完結し追加インストール不要。将来の機能追加にも十分対応できる |
| ORM | SQLAlchemy | FastAPIとの組み合わせで標準的。テストでのDB切り替え（本番用/テスト用）がしやすい |
| 認証方式 | セッションCookie方式（パスワードは`passlib`等でハッシュ化して保存） | 個人のローカルWebアプリにおける一般的で実装が素直な方式 |
| テストフレームワーク | pytest | Python標準的な選択。FastAPIの`TestClient`と組み合わせてAPIテストが容易 |

## 3. 開発方針
- **TDD**: 各機能について、先にテスト（pytest）を書き、それが通るように実装する。
- **拡張性**: 機能ごとにモジュールを分割する（例: `app/tasks/`, `app/auth/`, 将来の`app/files/`など）。新機能追加時に既存モジュールへの変更を最小限にする。
- **Git運用**: [CLAUDE.md](../CLAUDE.md) の構成に従う（`origin`=project2-devに日常push、`prod`=project2は明示指示時のみ反映）。

## 4. 機能要件（MVP: TODOタスク管理）

### 4.1 ユーザー認証
- ユーザー登録（ユーザー名・パスワード）
- ログイン／ログアウト
- 未ログイン状態でタスク関連ページにアクセスした場合はログインページへリダイレクト
- アカウント削除（本人確認のためパスワード再入力必須。削除するとそのユーザーが持つタスクも全て削除される）

### 4.2 タスク管理
- タスクの新規作成（タイトル必須、詳細・期限は任意）
- タスク一覧表示（ログインユーザー自身のタスクのみ表示）
- タスクの完了／未完了の切り替え
- タスクの編集（タイトル・詳細・期限）
- タスクの削除
- タスクの並び替え・絞り込み（完了/未完了でフィルタ、期限順ソート）※MVP後の拡張候補

### 4.3 データモデル（初期案）
- `User`: id, username, hashed_password, created_at
- `Task`: id, user_id (FK), title, description, due_date, is_done, created_at, updated_at

## 5. 非機能要件
- ローカル実行のみ。外部ネットワークへの公開は行わない。
- パスワードは平文で保存・ログ出力しない。
- 他ユーザーのタスクは参照・操作できないようにアクセス制御する。
- テストカバレッジ: 主要なAPIエンドポイント（認証・タスクCRUD）は全てテストで担保する。

## 6. 将来の拡張候補（スコープ外・検討事項）
- データ/ファイル処理ツール機能の追加（CSV集計など）
- 習慣化トラッカーなど、タスク管理以外の生活管理機能
- フロントエンドのReact等への移行（画面数が増え、素のHTML/JS管理が煩雑になった場合）
- タスクのカテゴリ分け・タグ機能
- 通知・リマインダー機能

以下は着手順を決めるための積み残しリスト。実装に着手するものは本章から4章（機能要件）に移す。

- ~~**タスクの編集機能**~~: 実装済み（2026-11-27、4.2章に反映）。
- ~~**アカウント削除機能**~~: 実装済み（2026-11-28、4.1章に反映）。
- **メールアドレス登録＋リマインド送信**: ドメイン取得は不要（既存メールアカウントの送信元利用で可）。ただし「指定日時に自動送信」にはスケジューラ的な仕組みが必要で、ローカルPCが起動していない間は送信できない制約がある。要検討。
- **タスクのカレンダー表示**: 既存の`due_date`を使って実現可能。カレンダーUIライブラリ導入 or 自作で検討。
- **期限を期間（開始日〜終了日）で入力**: データモデルに`start_date`相当の追加が必要。
- **日付入力UIの改善**: 現状はブラウザ標準の`<input type="date">`のみ。より直感的なUI（カレンダーピッカー等）を検討。
- **並び替え・ソート機能の仕様精緻化＋手動並び替え（ドラッグ&ドロップ）の記憶**: 自動ソート（期限順等）とは別に、ユーザーが手動で並べた順序を保持する仕組み（`sort_order`列相当）が必要。設計を詳しく練る必要がある大きめの機能。
